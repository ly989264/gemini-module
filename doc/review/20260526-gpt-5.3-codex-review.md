# gemini-bloom 实现挑刺（review）

> 评审时间：2026-05-26  
> 评审模型：gpt-5.3-codex

## 总体结论
当前 `gemini-bloom` 已具备较完整的 Redis Module 基础能力（建、查、批量查、持久化/恢复、基础测试），但在**并发与阻塞语义、兼容性边界、错误模型一致性、可观测性与可维护性**方面还存在提升空间。以下“挑刺”按风险优先级排列。

---

## P0 / 高风险问题

### 1) `BF.LOADCHUNK` 允许直接写位图，缺少一致性校验上下文
**现象**：当前实现对 chunk 长度做了严格匹配校验，这是正确的；但它仍依赖调用方按正确顺序、对正确层写入正确 bit-array。若业务侧误把 layer index / chunk payload 搞混，模块可成功写入但语义损坏。  
**风险**：出现“可加载但概率行为异常”的 silent corruption（不是 crash，而是概率失真）。  
**建议**：
- 增加可选校验信息（例如 layer hash/CRC 或 meta 摘要）并在 LOADCHUNK 前后做轻量校验。
- 提供 `BF.DEBUG.VALIDATE`（内部命令）用于检查 layer 元数据与 bit-array 一致性。

### 2) 缩容/扩容边界依赖隐式约束，缺少对极端参数的系统性保护
**现象**：扩容路径对 overflow 有处理思路，但对极端参数（超大 capacity、超小 error_rate、expansion 边界）组合的“连锁资源消耗”缺少统一 guard。  
**风险**：内存峰值骤升、单命令延迟抖动、OOM 概率增加。  
**建议**：
- 在 `Reserve/Insert` 热路径前，统一做 “next layer 预计内存” 的预算校验。
- 引入模块级上限（例如单 key 最大层数、最大总位图字节）。

---

## P1 / 中风险问题

### 3) 命令时延模型偏“同步大块操作”，对主线程友好度一般
**现象**：`SCANDUMP/LOADCHUNK` 与 RDB 读写均会进行大块内存拷贝。  
**风险**：在大 filter / 多层场景下，Redis 主线程停顿增大（tail latency 上升）。  
**建议**：
- 评估是否可分片处理与更细粒度让出（至少在未来版本中预留异步化接口）。
- 补充命令级“数据规模-耗时”基准报告，定义 SLO（例如 99p < X ms）。

### 4) 可观测性偏弱，线上排障手段不足
**现象**：日志主要是注册失败等初始化场景；运行态缺少结构化统计。  
**风险**：出现误判（容量规划、FPR 漂移）时难以快速定位。  
**建议**：
- 增加 INFO 子段：每层容量、itemCount、bytes、累计 bytes、expansion 次数。
- 增加失败计数器：参数错误、反序列化失败、chunk 校验失败等。

### 5) 兼容性策略写在注释里较多，自动化防回归不足
**现象**：RDB wire format 的兼容性说明清楚，但“兼容性契约”主要靠实现者自觉。  
**风险**：后续改动易引入字段顺序、版本分支行为偏差。  
**建议**：
- 把兼容矩阵固化为参数化测试（encVer × flags × expansion × layerCount）。
- 增加“黄金样本”二进制回归（fixtures），变更时强制对比。

---

## P2 / 低风险但建议优化

### 6) 错误码/错误文案的一致性可以再收敛
**现象**：不同命令在参数非法、类型不匹配、状态不合法时的报错风格可能不完全一致。  
**建议**：建立统一错误词典（prefix + reason + hint），利于 SDK / 业务侧自动处理。

### 7) 测试覆盖重点偏“正确性”，对性能退化与资源上限覆盖不足
**建议**：
- 增加压力型单测/集成测：大 key、深层扩容、频繁 dump/load。
- 增加 failpoint（分配失败、半包/坏包）验证恢复路径。

### 8) 文档可增加“生产参数建议模板”
**建议**：按场景提供推荐配置（小内存高 QPS / 大容量离线导入 / 低误判场景），减少误用。

---

## 我认为最值得优先改的 3 项
1. **完善 LOADCHUNK 防误写校验**（先把 silent corruption 风险压下去）。  
2. **建立扩容前内存预算 guard + key 级上限**（先兜底资源风险）。  
3. **补齐 RDB 兼容性黄金样本回归**（先守住跨版本协议稳定性）。
